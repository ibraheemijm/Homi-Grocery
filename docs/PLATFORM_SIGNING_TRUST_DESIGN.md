# تصميم سلسلة الثقة لمفاتيح Homi Platform

## الحالة

مقترح أمني للتنفيذ بعد مراجعة صاحب المشروع. لا يحتوي هذا المستند على مفاتيح فعلية أو أسرار نشر، ولا يفعّل الترخيص أو OTA للإنتاج.

## المشكلة الحالية

تجلب خدمات الترخيص والتحديث قوائم مفاتيح Ed25519 العامة من واجهات API نفسها التي تجلب منها التصاريح وبيانات الإصدارات. ثم تتحقق من التوقيع باستخدام المفتاح الذي أعاده الخادم.

هذا يثبت أن التصريح أو manifest وقّعه المفتاح الذي أعاده الخادم، لكنه لا ينشئ جذر ثقة مستقلًا بالتطبيق. إذا تمكن مهاجم من تغيير استجابة بيانات التحديث وقائمة المفاتيح معًا، يمكنه استبدال المحتوى والمفتاح والتحقق منهما معًا. HTTPS يحمي النقل المعتاد، لكنه لا يعوض غياب جذر ثقة مستقل عند اختراق الخادم أو حساب النشر أو قناة توزيع البيانات.

## التصميم المقترح

### 1. جذر ثقة مضمّن داخل التطبيق

- يضمّن التطبيق مفتاح Ed25519 عامًا واحدًا مخصصًا لتوقيع keyset، ويكون ثابتًا ضمن إصدار التطبيق.
- لا يغادر المفتاح الخاص المقابل بيئة الحفظ offline، ولا يوضع في GitHub أو خادم API أو أسرار CI.
- لا يُقبل أي مفتاح تشغيلي لمجرد أن API أعاده؛ يجب أولًا التحقق من توقيع keyset باستخدام الجذر المضمّن.
- لا يُستخدم مفتاح الجذر لتوقيع manifests أو تصاريح الترخيص مباشرة.

### 2. ملف Keyset موقع

تُرجع المنصة غلافًا يحتوي على:
- `payload`: النص الأصلي للـJSON بترميز UTF-8 ثم Base64.
- `signature`: توقيع Ed25519 للبايتات الأصلية نفسها باستخدام مفتاح الجذر.
- `root_key_id`: معرّف الجذر المتوقع.

يتضمن payload:
- `schema_version`
- `keyset_version` رقمًا تصاعديًا.
- `issued_at` و`expires_at`.
- قائمة `keys`، وكل عنصر يحتوي `key_id` و`purpose` و`algorithm` و`public_key` و`not_before` و`not_after` و`status`.

يجب التحقق من توقيع البايتات قبل تحليل محتوى payload أو استخدام أي مفتاح داخله. لا يعاد إنشاء JSON ثم توقيعه؛ التوقيع يكون على البايتات الأصلية المحددة في الغلاف.

### 3. فصل مفاتيح الاستخدام

تُخصص مفاتيح تشغيلية مختلفة على الأقل للأغراض التالية:
- `update_manifest`: توقيع بيانات إصدار التطبيق وروابط الحزمة وبصماتها.
- `offline_license_grant`: توقيع تصاريح الترخيص التي يتحقق منها التطبيق دون اتصال.

يرفض التطبيق المفتاح إذا كان `purpose` لا يطابق العملية، أو إذا كان الخوارزمية غير مدعومة، أو كانت صلاحية المفتاح لم تبدأ/انتهت، أو كانت حالته revoked. حالة `verify_only` تسمح بالتحقق من توقيعات قديمة فقط وفق سياسة صلاحية واضحة، ولا تسمح بتوقيع جديد.

### 4. منع الرجوع إلى Keyset أقدم

- يحتفظ التطبيق بأعلى `keyset_version` موثوق قبله، مع نسخة keyset الموقعة.
- يرفض أي keyset بإصدار أقل من الإصدار المحفوظ.
- يرفض تكرار `key_id` أو اختلاف المفتاح العام للمعرف نفسه داخل keyset واحد.
- يرفض keyset منتهي الصلاحية أو غير متسق زمنيًا.
- تُخزن حالة الإصدار الأعلى في تخزين محلي محمي قدر الإمكان. يجب توثيق أن التخزين المحلي وحده لا يمنع مالك الجهاز من التلاعب الكامل بجهازه أو استرجاع نسخة احتياطية قديمة.

### 5. التخزين المؤقت والعمل دون اتصال

- عند الاتصال، يتحقق التطبيق من keyset جديد ثم يحفظه ذريًا بعد نجاح التحقق الكامل فقط.
- عند انقطاع الشبكة، يمكن استخدام آخر keyset موقع ما زال ضمن سياسة الصلاحية.
- لا يُمدد التطبيق صلاحية keyset من تلقاء نفسه.
- يجب تحديد مدة صلاحية تشغيلية واضحة للـkeyset وسياسة مستقلة لمدة عمل تصريح offline؛ لا ينبغي افتراض أن تصريحًا غير منتهٍ يعني أن مفتاح توقيعه لم يُسحب.
- إذا انتهت صلاحية keyset ولا يتوفر اتصال لتحديثه، يتبع التطبيق سياسة offline محددة مسبقًا بدل قبول مفتاح غير معلوم الحالة.

### 6. تدوير المفاتيح وإلغاؤها

- تُنشأ مفاتيح التشغيل وتُحفظ خارج التطبيق وفي بيئة نشر محمية.
- ينشر keyset جديد موقع بالجذر، ويمكن أن يتضمن المفتاح الجديد بحالة active والقديم verify_only لفترة انتقال.
- بعد انقضاء فترة الانتقال، يُحوّل المفتاح القديم إلى revoked أو يُزال وفق سياسة الاحتفاظ بالتحقق من التصاريح القديمة.
- في الإصدار الأول، تغيير جذر الثقة نفسه يتطلب إصدار تطبيق جديد يضمّن الجذر الجديد. لا توجد آلية تبديل جذر عن بعد في هذه المرحلة.
- أي دعم مستقبلي لتدوير الجذر يحتاج بروتوكول انتقال متقاطع التوقيع ومراجعة مستقلة قبل التنفيذ.

## قواعد التحقق الإلزامية

1. رفض keyset دون توقيع أو بتوقيع غير صحيح.
2. رفض keyset موقع بمفتاح جذر غير معروف.
3. رفض `root_key_id` لا يطابق الجذر المضمّن.
4. رفض إصدار keyset أقدم من أعلى إصدار محفوظ.
5. رفض keyset منتهي الصلاحية أو بتاريخ إصدار مستقبلي خارج هامش الساعة المعتمد.
6. رفض key IDs مكررة أو مفاتيح عامة بصيغة/طول غير صحيح.
7. رفض مفتاح لغرض غير مطابق، أو منتهي الصلاحية، أو revoked.
8. رفض manifest أو تصريح offline إذا لم يوجد مفتاح تشغيلي موثوق ومصرح للغرض المحدد.
9. رفض توقيع manifest أو التصريح إذا لم يطابق التوقيع payload الأصلي.
10. عدم تحديث النسخة المخبأة أو رقم الإصدار الأعلى إلا بعد اكتمال كل التحققات.

## إدارة المفاتيح خارج التطبيق

- مفتاح الجذر الخاص: محفوظ offline، ومتاح لأشخاص محدودين جدًا، ولا يوضع ضمن CI.
- مفاتيح توقيع manifests والتراخيص: تحفظ في KMS أو Secret Store محمي، مع صلاحيات منفصلة وسجل تدقيق.
- لا تُطبع المفاتيح أو التواقيع السرية أو الرموز في CI logs.
- مفاتيح الاختبار فقط تكون fixtures معلنة بوضوح، ولا تُقبل في إعدادات الإنتاج.
- لا ينشئ المطور أو CI مفاتيح إنتاجية تلقائيًا، ولا يستبدل مفاتيح يملكها صاحب التطبيق.

## خطة التنفيذ بعد اعتماد التصميم

1. اعتماد تنسيق keyset النهائي ومدة صلاحيته وسياسة offline.
2. إضافة Root Key Verifier مستقل مع مفتاح اختبار فقط في الاختبارات.
3. إضافة Keyset parser/validator واختبارات التوقيع والتواريخ والتكرار والتراجع.
4. تعديل خدمتي الترخيص والتحديث لاستخدام Keyset موثوق بدل قبول قوائم مفاتيح API مباشرة.
5. إضافة تخزين ذري للـkeyset وأعلى إصدار موثوق.
6. إضافة اختبارات إلغاء المفتاح وتدويره ورفض downgrade.
7. توثيق عملية توليد ونشر keyset ومفاتيح التشغيل لدى إدارة المنصة.
8. إجراء مراجعة أمنية واختبارات CI قبل ربط OTA أو الترخيص بالإنتاج.

## قرارات مطلوبة قبل التنفيذ الإنتاجي

- مدة صلاحية keyset: القيمة المقترحة 30 يومًا.
- مهلة سماح للساعة عند التحقق من `issued_at`: القيمة المقترحة 5 دقائق.
- مدة الاحتفاظ بمفتاح قديم بحالة verify_only: تُحدد بحسب أطول مدة تصريح offline معتمد.
- سياسة انتهاء keyset دون اتصال: يوصى بالسماح باستخدام keyset مخزن فقط حتى `expires_at`، ثم طلب اتصال قبل إصدار/تجديد تصريح offline أو اعتماد تحديث جديد.
- جذر الثقة الأول: يقدمه مالك المشروع أو يعتمد طريقة إنشائه وحفظه offline؛ لا ينشأ تلقائيًا داخل CI.
