# خطة المشروع ونقطة الاستئناف — Homi Grocery

> هذه الوثيقة هي مرجع الاستئناف عند انقطاع الاتصال أو بدء محادثة جديدة. قبل أي تعديل، اقرأها ثم افحص الملفات الحالية ونتيجة CI؛ لا تعتمد على هذه الوثيقة وحدها إذا كان الكود قد تغيّر.

## الهدف والقرارات المعتمدة

- اسم التطبيق: **Homi Grocery**.
- التقنية: Flutter وSQLite محليًا، يعمل دون اتصال بالإنترنت.
- ترتيب المنصات: نسخة Linux على Manjaro أولًا، ثم Android، ثم Windows عبر GitHub Actions.
- الواجهة عربية RTL، مع دعم الثيم الفاتح/الداكن تلقائيًا، وتصميم Liquid Glass متوازن.
- الألوان: أخضر داكن `#173D32`، كريمي `#F7F4EA`، ذهبي `#C7A35A`، وأخضر فاتح `#DCE9DF`.
- العملة الافتراضية الجنيه السوداني، ويجب أن تكون قابلة للتغيير لاحقًا.
- السماح بالمخزون السالب مع تحذير واضح وتسجيله، بدل منع البيع.
- عدم دمج Pull Request قبل نجاح التحليل والاختبارات والبناء.

## النطاق الوظيفي الكامل

1. **الأصناف والمخزون:** إضافة وتعديل وأرشفة وبحث، باركود، وحدات وأسعار شراء/بيع، كميات وحد إعادة الطلب، وحركات مخزون موثقة.
2. **المبيعات والفواتير:** سلة، خصم، فاتورة مرقمة، نقدي وآجل وجزئي، حفظ ذري للفاتورة وبنودها وتحديث المخزون.
3. **الزبائن ودفتر الديون:** ملفات الزبائن، الأرصدة، التحصيلات، كشف حساب وحركة الرصيد.
4. **الموردون والمشتريات:** الموردون، فواتير الشراء، زيادة المخزون، المبالغ المستحقة والمدفوعات.
5. **الخزينة:** المقبوضات والمدفوعات والمصروفات، الرصيد، فتح وإغلاق الورديات وتسوية الكاشير.
6. **التقارير:** المبيعات والأرباح والمخزون المنخفض والديون والتحصيلات والمشتريات والمصروفات وتقارير حسب التاريخ.
7. **الطباعة:** فواتير وإيصالات وتقارير، مع دعم الطابعات الحرارية قدر الإمكان.
8. **الحماية:** تسجيل الدخول، أدوار المدير والكاشير، صلاحيات واضحة، سجل تدقيق للأعمال الحساسة.
9. **النسخ الاحتياطي والاستعادة:** نسخ قابلة للتحقق، واستعادة آمنة مع تنبيه قبل الاستبدال.
10. **الإعدادات والجودة:** العملة، بيانات المتجر، التفضيلات، الاستمرارية، معالجة الأخطاء، واختبارات تغطي المسارات الحساسة.

## الحالة الحالية المعروفة

الفرع العامل: `feature/flutter-foundation`  
Pull Request: https://github.com/ibraheemijm/Homi-Grocery/pull/1  
CI: https://github.com/ibraheemijm/Homi-Grocery/actions

الموجود في الكود حتى آخر نقطة استئناف:
- هيكل Flutter والواجهة الرئيسية العربية RTL والهوية البصرية.
- قاعدة بيانات SQLite محلية مع ترحيلات إصدار المخطط.
- مستودع الأصناف وواجهة الأصناف.
- البيع وحفظ الفواتير وبنودها وتحديث المخزون.
- طرق الدفع نقدي/جزئي/آجل والتحقق من توافق المدفوع مع نوع الدفع.
- قاعدة بيانات الزبائن وربط الفواتير بالزبائن وترحيل أسماء الزبائن القديمة.
- دفتر أرصدة الزبائن وتسجيل التحصيلات مع منع التحصيل الزائد.
- إحصاءات لوحة التحكم موصولة بقاعدة البيانات.
- اختبارات مستودعات الأصناف والمبيعات والزبائن والإحصاءات واختبار واجهة أساسي.

**تنبيه استئناف:** آخر تشغيل CI المعروف انتهى بالفشل بسبب خطأ تحليل في `app/lib/main.dart` عند السطر 493: استخدام `const Expanded` مع نص يتغير حسب حالة الإحصاءات. أُزيلت `const` عن `Expanded` في commit إصلاح لاحق؛ يجب التحقق من نتيجة CI الجديدة وعدم اعتبار الإصلاح ناجحًا قبل ظهور نجاح فعلي للتحليل والاختبارات والبناء.

## قواعد العمل الإلزامية قبل كل مرحلة

1. افحص آخر commit والفرع وحالة Pull Request ونتائج GitHub Actions.
2. اقرأ الملفات ذات الصلة، والمخطط وقواعد البيانات والترحيلات والاختبارات قبل تغييرها.
3. تتبع التدفق كاملًا من الواجهة إلى المستودع وقاعدة البيانات، ولا تعالج العرض فقط إذا كان الخلل في المنطق.
4. حافظ على التوافق مع البيانات الموجودة؛ أي تغيير في المخطط يتطلب ترحيلًا آمنًا واختبارات ترحيل.
5. اكتب التعليقات والتوثيق الموجّه للمستخدم بالعربية، واجعل أسماء الرموز البرمجية واضحة ومتسقة.
6. بعد التعديل شغّل `flutter format` للملفات المتغيرة، ثم `flutter analyze` و`flutter test` و`flutter build linux` من مجلد `app` متى توفرت البيئة.
7. إذا تعذر الاختبار المحلي، لا تدّعِ نجاحه؛ استخدم CI وانتظر النتيجة النهائية للـ commit الحالي.
8. أصلح كل خطأ مكتشف وأعد الاختبارات. لا تكدّس ميزات جديدة فوق فشل قائم.
9. لا تدمج PR من تلقاء نفسك، ولا تحذف بيانات أو تغيّر سلوكًا معتمدًا دون مبرر واضح.
10. حدّث هذه الوثيقة عند اكتمال كل مرحلة، مع ذكر آخر commit، ونتائج الاختبارات، والخطوة التالية.

## خطة التنفيذ المتتابعة

### المرحلة 0 — تثبيت الجودة (الحالية)
- فحص CI الحالي وإصلاح أخطاء التحليل والاختبارات والبناء حتى النجاح.
- مراجعة ترحيلات قاعدة البيانات، العلاقات، قواعد الدفع والتحصيل، حساب الديون وإحصاءات لوحة التحكم.
- إضافة/تحسين اختبارات لحالات الحواف والأخطاء، والتأكد من أن جميع الاختبارات مستقلة.
- مراجعة التغييرات كاملة والتأكد من أن الواجهة لا تنهار عند قاعدة بيانات فارغة أو خطأ في التحميل.

### المرحلة 1 — إكمال الأصناف والمخزون
- التحقق من الحقول والأسعار والوحدات والباركود وحد إعادة الطلب.
- حركات المخزون (إضافة، تسوية، مرتجع بيع/شراء) مع سجل تدقيق.
- اختبارات تمنع تلف الأرصدة وتوضح سياسة المخزون السالب.

### المرحلة 2 — إكمال المبيعات والزبائن
- كشف حساب زبون مفصل بالرصيد الافتتاحي والفواتير والتحصيلات والمرتجعات.
- مرتجعات المبيعات واسترداد المبالغ وتعديل المخزون بطريقة ذرية.
- تحسين التحقق من المدفوعات الجزئية وحالات الفاتورة وإظهار الأرصدة بوضوح.
- تحديد كيفية توزيع التحصيل على الفواتير؛ لا تخلط التحصيلات العامة مع رصيد فاتورة دون توثيق.

### المرحلة 3 — الموردون والمشتريات
- قاعدة بيانات الموردين، فواتير الشراء وبنودها، تحديث المخزون، المدفوعات والديون.
- اختبارات الحفظ الذري والترحيلات والرصيد المتبقي.

### المرحلة 4 — الخزينة والورديات
- مصروفات ومقبوضات مستقلة، حركات خزينة، فتح/إغلاق وردية، تسوية الرصيد، فصل صلاحيات المدير والكاشير.

### المرحلة 5 — التقارير
- تقارير قابلة للتحقق ومحددة بالفترة: المبيعات، الأرباح، المخزون، الديون، التحصيلات، المشتريات والمصروفات.
- اختبار الحسابات على بيانات معروفة، لا تعتمد على قيم واجهة ثابتة.

### المرحلة 6 — الطباعة
- تصميم فاتورة A4 وإيصال حراري، إعدادات الطابعة، اختبار التفاف النص العربي والأرقام والعملات.

### المرحلة 7 — الحماية والنسخ الاحتياطي
- تسجيل الدخول والأدوار والصلاحيات وسجل التدقيق.
- نسخ احتياطي واستعادة مع فحص الملف، معالجة الفشل وعدم استبدال قاعدة سليمة بنسخة تالفة.

### المرحلة 8 — تثبيت Linux ثم Android ثم Windows
- بناء وتشغيل Linux على Manjaro، واختبار العمليات الأساسية فعليًا.
- إعداد Android SDK والبناء وتجربة APK على الهاتف.
- إعداد بناء Windows عبر CI والتحقق من التبعيات والطباعة.
- مراجعة نهائية للتوثيق، التثبيت، الترحيلات، الاختبارات، وإصدار نسخة تجريبية.

## الخطوة التالية عند الاستئناف

ابدأ دائمًا بفحص أحدث حالة للفرع ونتيجة CI للـ commit الحالي. إن فشل أي فحص، أصلح الفشل وأعد التشغيل. بعد نجاح المرحلة 0، تابع المرحلة 1 ثم بقية المراحل بالتسلسل، مع تحديث هذه الوثيقة في كل نقطة توقف.
