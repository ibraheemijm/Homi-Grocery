# تصميم استكمال تحديث Windows الآمن (OTA)

## الحالة

هذه الوثيقة تصف تصميم الاسترداد والتنفيذ المرحلي الحالي. أُنفذ بروتوكول commit/rollback وفحص صحة بدء التشغيل في الفرع، لكن OTA لا يزال غير مربوط بواجهة التطبيق أو خادم الإنتاج ولا يُعد جاهزًا للنشر.

## الأهداف الأمنية
1. يبقى تطبيق Homi Grocery دائمًا بصلاحيات المستخدم العادية (asInvoker).
2. تُحصر صلاحيات المسؤول في عملية التبديل الضرورية داخل مساعد مستقل.
3. لا يشغّل المساعد المرتفع التطبيق الجديد بنفسه.
4. لا يُعتبر التحديث ناجحًا بمجرد فك ZIP أو تبديل المجلدات؛ يجب أن يفتح التطبيق الجديد قاعدة البيانات المحلية ويجتاز تهيئة بوابة الدخول.
5. عند فشل التهيئة أو انقطاع المنسق، تعود ملفات الإصدار السابق تلقائيًا.
6. لا تُنقل قاعدة بيانات المتجر أو الصور أو الخطوط أو النسخ الاحتياطية مع ملفات البرنامج.

## العمليات والمسؤوليات

### 1. تطبيق Flutter (صلاحيات المستخدم)
- يتحقق من وجود تحديث وبيانات الحزمة قبل بدء العملية.
- ينزّل الحزمة إلى مجلد مؤقت خارج مجلد التثبيت، ويتحقق من SHA-256.
- يطلق HomiUpdateLauncher.exe دون Verb=runas وبصلاحياته الحالية، ويمرر PID ومسار التثبيت والحزمة والبصمة.
- يغلق واجهته بعد أن يؤكد المنسق أنه بدأ الإجراء.
- لا يشغّل HomiUpdater.exe مباشرة.

### 2. HomiUpdateLauncher.exe (منسق بصلاحيات المستخدم)
- يعمل كـ asInvoker، ويظل حيًا طوال العملية.
- ينشئ اسم Named Pipe عشوائيًا ورمز nonce عشوائيًا، ويقيّد الاتصال بالمستخدم الحالي.
- يطلق HomiUpdater.exe باستخدام Windows Shell runas، وهو مسار UAC الرسمي لطلب الرفع عند الحاجة فقط.
- يستقبل عبر القناة نتيجة التبديل، ثم يشغّل التطبيق الجديد بنفس token المنسق غير المرتفع.
- يمرر للتطبيق مسار ملف health marker ورمز nonce كوسيطين خاصين بسطر الأوامر؛ لا تُستخدم متغيرات بيئة عامة.
- ينتظر إشارة الجاهزية بمهلة محددة (مبدئيًا 60 ثانية، قابلة للضبط والاختبار).
- يرسل قرار commit أو rollback إلى المساعد المرتفع عبر القناة نفسها، بعد مطابقة marker مع nonce.
- إذا مات التطبيق أو لم تصل إشارة الصحة في الوقت المحدد، يطلب التراجع.
- لا يكتب في مجلد Program Files ولا يغير ملفات التطبيق بنفسه.

### 3. HomiUpdater.exe (مساعد مرتفع)
- يبقى مسؤولًا عن التحقق من المدخلات والحزمة واستخراجها والتبديل على نفس القسم.
- بعد نقل المجلد القديم إلى backup ونقل stage إلى install، لا يعتبر العملية نهائية.
- يتصل بقناة المنسق ويتحقق من nonce، ثم يرسل رسالة installed التي تعني أن التبديل اكتمل فقط، لا أن التطبيق اجتاز فحص الصحة.
- ينتظر قرارًا محدود الوقت: commit يثبت التبديل، rollback يعيد backup إلى مسار التثبيت، وانقطاع القناة أو انتهاء المهلة يعامل كـ rollback. وعند الاسترجاع يحاول إيقاف أي عملية جديدة تعمل من مسار التثبيت.
- لا يشغّل ملف Homi التنفيذي مطلقًا.
- يتحقق قبل التراجع من أن install وbackup هما المساران المتوقعان، وأنهما مجلدان حقيقيان وليسا Reparse Points.
- لا يحذف backup قبل تأكيد القرار النهائي.

## بروتوكول الاتصال
- قناة محلية Named Pipe باسم عشوائي، مع تقييدها للمستخدم الحالي.
- كل رسالة تحتوي nonce نفسه، وإصدار البروتوكول، ونوع الرسالة.
- رسائل الإصدار الأول المستخدمة حاليًا: installed، commit، rollback. لا يوجد إقرار منفصل بعد استلام قرار commit/rollback.
- لا تُقبل أوامر بدون nonce مطابق أو رسالة خارج التسلسل.
- يجب تحديد حد لحجم الرسالة، ووقت اتصال/قراءة، وعدم الاعتماد على اسم pipe وحده كإثبات للهوية.

## فحص صحة التطبيق الجديد
- تقرأ نقطة تشغيل Flutter وسيطي سطر الأوامر الخاصين بعلامة الصحة، ولا تقبل nonce إلا إذا كان بصيغة 64 حرفًا سداسيًا وعلى Windows فقط.
- بعد نجاح فتح قاعدة البيانات في AuthenticationGate._initialize ونجاح AuthRepository.hasAccounts، تكتب البوابة marker ذريًا عبر ملف مؤقت ثم إعادة تسميته، ويحتوي nonce إلى المسار المحدد.
- لا يحتوي الملف على بيانات متجر أو أسرار. لا تُكتب إشارة الجاهزية عند مجرد runApp أو أول frame؛ لأن ذلك لا يثبت أن قاعدة البيانات قابلة للفتح.
- إذا لم تكن متغيرات التحديث موجودة، لا يفعل المكوّن شيئًا ويستمر التطبيق كالمعتاد.

## إدارة النسخ الاحتياطية
- تظل نسخة الإصدار السابق بجوار مجلد التثبيت على القسم نفسه.
- لا تُحذف عند التبديل الأولي.
- بعد commit، يحتفظ النظام بآخر نسخة سابقة واحدة على الأقل؛ تزال النسخ الأقدم فقط بعد نجاح تحديث لاحق وبسياسة تنظيف منفصلة.
- عند rollback، لا تُحذف ملفات الإصدار الفاشل فورًا؛ يمكن الاحتفاظ بها مؤقتًا لتشخيص السبب، مع منع تشغيلها.
- لا يلمس أي مسار من هذه المسارات مجلد بيانات المتجر.

## حالات الفشل التي يجب اختبارها
1. رفض UAC أو إلغاء المستخدم: لا تتغير ملفات التثبيت، ويظل التطبيق القديم صالحًا.
2. خطأ التحقق من SHA-256 أو ZIP: لا تتغير ملفات التثبيت.
3. فشل الاستخراج: لا تتغير ملفات التثبيت ولا يبقى stage.
4. فشل نقل install إلى backup: يظل التطبيق القديم في مكانه.
5. فشل نقل stage إلى install: يعاد backup تلقائيًا.
6. انقطاع Named Pipe بعد التبديل وقبل تشغيل التطبيق: rollback تلقائي.
7. فشل تشغيل الملف التنفيذي الجديد: rollback.
8. بدء التطبيق ثم فشل فتح SQLite أو تهيئة AuthenticationGate: لا marker، ثم rollback.
9. انتهاء مهلة الصحة: rollback.
10. وصول nonce خاطئ أو رسالة غير مرتبة: رفض الرسالة والرجوع الآمن.
11. نجاح الصحة ثم commit: يظل الإصدار الجديد في مكانه وتُحفظ نسخة سابقة.
12. فشل rollback نفسه (مثل انقطاع القرص أو منع الوصول): لا تُحذف النسخة الاحتياطية أو ملفات الإصدار الجديد، ويظهر خطأ واضح مع المسارات التشخيصية.

## مراحل التنفيذ والحالة
1. [مكتمل مبدئيًا] بناء Launcher بصلاحيات asInvoker وطلب UAC للمساعد فقط.
2. [مكتمل مبدئيًا] Named Pipe وnonce ورسائل مؤطرة بحد 4 KiB.
3. [مكتمل مبدئيًا] انتظار قرار commit/rollback، مع rollback تلقائي عند انقطاع القناة أو انتهاء مهلة المساعد.
4. [مكتمل مبدئيًا] health marker بعد فتح SQLite وفحص وجود الحسابات في AuthenticationGate.
5. [قيد التحقق] اختبارات Windows على GitHub Actions لقرار commit وrollback وانقطاع القناة، ثم اختبار عملي على Windows 10/11.
6. [لم يبدأ] ربط Flutter بالمنسق في تدفق OTA، وإعداد عنوان المنصة والتحقق من توقيع manifest قبل أي تحديث إنتاجي.


## التنفيذ الحالي

- أُضيف مشروع `installer/windows-updater-launcher/` مستقل، وملف manifest يحدد `asInvoker` صراحةً.
- ينشئ المنسق Named Pipe باسم عشوائي ورمز nonce عشوائيًا بطول 256 بت، مع `PipeOptions.CurrentUserOnly` لتقييد الاتصال بحساب Windows الحالي.
- يطلق المنسق `HomiUpdater.exe` عبر `UseShellExecute=true` و`Verb=runas`؛ لذلك لا تُرفع صلاحيات تطبيق Flutter أو المنسق نفسه.
- رسائل البروتوكول مؤطرة بطول مسبق، بحد 4 KiB، ومهلة اتصال/قرار 150 ثانية، والتحقق من إصدار البروتوكول ونوع الرسالة ومطابقة nonce بزمن ثابت.
- بعد رسالة `installed` يشغّل المنسق التطبيق الجديد بصلاحياته العادية، وينتظر health marker لمدة 60 ثانية.
- تكتب Flutter علامة الصحة ذريًا بعد نجاح فتح SQLite وفحص `AuthRepository.hasAccounts()` ضمن `AuthenticationGate`.
- عند غياب marker أو إغلاق التطبيق أو فشل تشغيله، يرسل المنسق `rollback`. وعند انقطاع القناة يعيد المساعد النسخة السابقة تلقائيًا ويحاول إيقاف التطبيق الجديد أولًا.
- يحتفظ المساعد بنسخة الإصدار السابق بعد `commit`؛ لم تُنفذ سياسة تنظيف النسخ الأقدم.
- أضيفت اختبارات smoke لقرار commit وrollback وانقطاع القناة، ويُبنى المنسق ضمن Windows CI ويُثبت خارج مجلد التطبيق داخل `ProgramData`.

هذه المرحلة لا تزال بحاجة إلى اجتياز CI على آخر commit واختبار فعلي على جهاز Windows مع UAC. لم يُربط تدفق OTA بواجهة Flutter أو بخادم الإنتاج، ولذلك لا يجوز تفعيل التحديث للمستخدمين بعد.

## حدود الثقة
- SHA-256 يثبت تطابق الملف مع قيمة متوقعة، لكنه لا يثبت وحده أن مصدر التحديث موثوق. يلزم توقيع manifest رقمي والتحقق من التوقيع بمفتاح عام مضمّن قبل تفعيل OTA الإنتاجي.
- عنوان Homi Platform API ومفاتيح توقيع manifest غير مضبوطة حاليًا؛ لا تُخترع أو تُضمّن قيم إنتاجية.
- لا توجد حتى الآن واجهة إنتاجية في Flutter لبدء OTA، ولا إعداد موثوق لمصدر manifest أو مفاتيحه؛ اختبارات البروتوكول الحالية لا تغني عن اختبار Windows ميداني.
